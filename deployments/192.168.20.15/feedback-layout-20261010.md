- 处理状态使用带数量的横向页签，默认“待处理、全部评价”。各状态数量互不重叠，并随其他筛选条件更新。

## 群聊现场复验结果与后续修复边界

用户使用企业微信 Windows 5.0.11.6029，在 18:41:17 发起新的群聊提问；18:41:31 回答结束。用户确认切换其他会话再返回，反馈入口仍会消失。因此本次不能宣称群聊问题已修复。

新增日志抓到以下证据：

- 首帧与结束帧使用同一个 UUID stream ID，且均带 `feedback=true`。
- 相同请求收到多次 `code=6000`，错误为 `more than one callers at the same time, data version conflict. please retry later`。结束发送附近同样有 6000，也有 code=0 回执；当前同一请求多帧并发在途，无法将这些回执准确一一对应到具体内容帧。
- 数据库中本次反馈目标存在，关联的助手回答 `is_completed=true`，持久化回答长度 6798 字符。没有因用户切换窗口删除反馈目标的服务端逻辑。
- 代码按约 300ms 刷新替换内容，发送只等待本地 WebSocket 写入，不等待平台回执；最终内容替换与 finish=true 紧接发送。平台返回的 6000 在原实现中没有传回发送方触发重试。
- [企业微信官方 SDK 发送队列实现](https://github.com/WecomTeam/aibot-node-sdk/blob/main/src/ws.ts) 针对同一个 req_id 串行发送并等待回执，当前 Go 适配器缺少对应机制。

结论：已确认机器人发送链路存在平台更新冲突，且原日志会把 socket 写入成功误当成回复成功。它是需要修复的明确缺陷，但仅凭以上日志，仍不能断言它是企业微信切换历史会话后按钮消失的唯一原因。

建议下一步修复：按 req_id 串行等待确认，不同提问独立处理；合并中间帧，避免积压；明确处理 6000、断线与超时；最终答案及 finish=true 必须获得平台确认，失败不能报告成功。应补充延迟回执、6000、超时、断线与多用户并发测试，然后再次实测“回答完成→切换会话→返回→点击评价→工作台收到反馈”。这部分发送队列重构尚未包含在本次部署中。

## 进一步只读排查（2026-10-10 19:00 后）

- 18:41 的同一请求共有 8 次 code=6000、39 次 code=0。并非所有帧失败，也不能将最后的成功回执直接等同于 finish=true 成功。
- 服务器只有一个应用容器、一个启用的企业微信 WebSocket 渠道，模式为 stream。所查日志没有重连、被新连接踢下线或重复建立该回复的记录；没有证据表明多位用户同时提问导致本次问题。
- 本次反馈目标仍在数据库中，切换会话未导致其被删除。
- 直接核对企业微信[接收事件文档](https://developer.work.weixin.qq.com/document/path/101027)：官方反馈事件示例明确使用 `chattype=group`，因此不能认为群聊天然不支持反馈。
- 核对[被动回复文档](https://developer.work.weixin.qq.com/document/path/101031)：`stream.feedback.id` 是首次回复设置的反馈回调关联标识。官方还说明，不设置反馈信息时，用户点击反馈不会触发回调。该字段不能直接当作客户端“始终显示反馈按钮”的开关。
- 官方文档没有提供可由服务端配置的“切换会话后仍显示原生反馈按钮”参数。发送冲突是已确认缺陷；客户端重载历史消息的展示行为仍需单独对照，不能用修改 feedback.id 替代验证。

下一步验证应先修复按请求等待回执、失败重试及结束确认，再用新回答做电脑和手机历史会话对照。已发送的历史消息不能假设会随部署自动恢复按钮。如果无冲突且结束确认成功的新消息仍出现问题，再调查平台历史消息限制或补充独立反馈卡片；卡片需另验保存行为及操作有效期，不能承诺永久可用。本轮仅更新排查记录，未修改应用代码、线上配置或发送测试群消息。
