# 企业微信历史回答反馈入口排查（2026-10-12）

## 现场结论

用户确认：回答完成时，底部有“有用／无用”；切到其他会话后返回，底部按钮消失，悬停不恢复。单聊、群聊均有该现象；手机查看也没有底部入口。

本轮新增对照：用户在已经没有底部按钮的历史回答上右键，确认菜单中仍有反馈入口，并通过该入口实际提交反馈。后台收到并保存了反馈。

因此，这次现象是客户端重新进入会话后没有恢复底部快捷入口，不能再称为“历史回答不能反馈”或“反馈关联丢失”。消息菜单的反馈仍然有效。公开协议没有解释底部快捷区的历史展示策略，尚不能断言这是产品设计还是客户端缺陷。

## 独立确认的发送缺陷

最近 48 小时日志找到 6 条带 UUID 的流式回复，均为群聊；拒绝次数分别为 8、2、2、14、3、4。不能据此声称已经取得单聊现场发送日志。19:49 的回答虽然有 2 次冲突，但 19:50 已成功收到“有用”反馈。

隔离测试使用部署服务器现有的 Linux 构建环境及当前源码，测试步骤完全断网，只连接测试进程内的模拟 WebSocket：

1. 分别模拟 direct/group 发送。
2. 保持反馈 ID 正确且稳定。
3. 模拟平台拒绝结束帧，返回 code=6000。
4. 两种会话均复现：`EndStream` 在收到平台确认前已经返回 nil、删除缓冲，随后平台拒绝不会传回调用者。

`TestDiagnosticRejectedFinishIsReportedSuccessful` 的两个子测试及现有两项 `TestWeComFeedback*` 测试均通过；这里“通过”表示成功复现缺陷，不表示发送缺陷已修复。该诊断用例放在本目录 `diagnostics` 中，不加入正常生产测试包；将来修复等待确认后，此复现用例应不再成立。

Windows 首次尝试因现有 PostgreSQL 查询解析依赖缺少本地 CGO 支持，编译失败；随后在隔离 Linux 构建容器完成验证。

远端测试材料：`/tmp/wecom-feedback-probe-20261012-zzrTVZ`；日志：该目录 `result.log`。诊断构建没有部署、没有重启服务，也没有向企业微信发送测试消息。

该发送缺陷需要单独修复，但现有证据不能把它等同于底部快捷按钮消失的原因。历史消息右键反馈已验证有效，先前“反馈关联可能没有保存”的推测在本轮所测消息上已被排除。

## 协议依据与后续方向

- [企业微信接收事件](https://developer.work.weixin.qq.com/document/path/101027)：设置反馈信息后，用户评价可触发反馈回调。
- [企业微信被动回复](https://developer.work.weixin.qq.com/document/path/101031)：首次回复的 `stream.feedback.id` 关联回调；未提供强制常显底部反馈按钮的参数。
- [企业微信长连接协议](https://developer.work.weixin.qq.com/document/path/101463)：流式回复及反馈事件协议。
- [WeKnora 上游反馈功能讨论](https://github.com/Tencent/WeKnora/issues/2813)：右键消息入口的调查线索；该讨论不作为企业微信正式 UI 展示规则。

现阶段用户可以通过历史回答的右键菜单反馈。若需要重新进入会话后仍能直接看到操作按钮，可进一步设计消息内的显式反馈卡片，并单独验证历史显示、有效期、身份绑定和重复点击行为；本轮没有实施该功能。
