# 故障问答先澄清再检索（2026-10-14）

## 行为与使用方式

- Web 和企业微信使用“仅基于知识库”的快速问答时，宽泛故障问题先确认产品/服务和具体报错，每轮最多追问两项。
- 用户在同一会话继续补充，系统合并已确认事实；已经回答的项目不重复询问。
- 已验证的产品、报错等事实随短期会话状态保存，后续模型提取遗漏时仍能沿用；“升级失败”等笼统文字不能被当作具体报错。状态继续兼容先前保存的纯文本记录。
- 检索到多套适用条件不同的方案时，继续确认影响方案选择的数据库、版本、部署方式等条件。信息充分后才生成有知识引用的答案。
- “xtwin 是什么”等一般知识问题正常检索回答。没有适用知识、检查失败、输出不完整时明确说明，不将失败当成有效处理建议。
- 故障上下文按空间、实际提问人、会话和智能体隔离，30 分钟过期；换话题清除旧故障。多次补充仍没有有效信息时建议人工核对。
- 个人记忆、以前生成的答案、其他知识案例中的版本与环境不作为本次故障事实。纯追问阶段不调用个人记忆，也不触发该轮记忆提炼。

例如：

1. 用户：升级失败了怎么办？机器人：询问产品/服务和具体报错。
2. 用户：是 KE 平台升级。机器人：只继续询问具体报错/失败步骤。
3. 用户补充报错原文或清晰截图。机器人检查是否还缺少决定处理方案的条件，条件齐全后引用适用知识回答。

无需员工额外配置。群聊只合并该提问者在对应会话中的故障信息，不合并其他群成员的补充。

## 管理员操作入口

- 问答统计 → 问答明细 → 查看：查看“等待补充信息”“建议人工核对”“无适用知识”等状态和本次实际回复。
- 回答反馈 → 查看/处理 → 发布前问答预演：选择期望“回答并引用知识”或“先追问补充信息”。
- 如果原始问题太宽泛，但要验证具体纠错答案，在“已确认的场景补充”中填写真实产品、报错和适用条件，再运行“应回答”预演。
- “应追问”通过仅代表追问行为正确，不作为纠错知识发布依据。发布仍需要完整场景下的回答预演通过；发布后还需真实索引复验。
